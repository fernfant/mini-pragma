Part 1 · the big picture

GPT-3 is a family, not one model

When people say "GPT-3" they picture the 175-billion-parameter giant that needed thousands of GPUs. But the GPT-3 paper (Table 2.1) actually defines 8 sizes — from 125M to 175B — all with the identical recipe. The small ones are real, honest GPT-3s. The 125M is the baby of the same family, and the model we build here is its little sibling.

Wait — what's a "head"? (the column above)

Back in Lesson 3, each word looked at the others and asked one question — which words matter to me right now? An attention head is one of those question-askers. Multi-head attention just runs several side by side: head 1 might learn to track which noun a verb belongs to, head 2 who the subject is, head 3 nearby words — each watching for a different kind of link, and their answers get stitched back together. More heads = more kinds of relationship the model can notice at once (our minigpt has 4; GPT-3 175B has 96). The term is real — it's exactly what the field calls it, straight from the 2017 paper Attention Is All You Need. (Heads-up: later on this page "output head" means something different — the final layer that turns vectors into word scores. Same word, unrelated job.)

Everything in this table runs the same code. The difference between your laptop model and the giant is which numbers you type into the config. Here are the four dials:

Part 2 · the one real token change

Characters → subword pieces (BPE)

4g read one character at a time (~25 ids). Real GPTs use a middle ground called BPE (byte-pair encoding): common words stay whole, rare words split into chunks, right down to single letters when needed. Best of both — short to read, but able to spell anything. We borrow GPT-2's exact tokenizer via tiktoken — a fixed vocabulary of 50,257 pieces, the same one OpenAI shipped.

enc = tiktoken.get_encoding("gpt2")   # GPT-2 / GPT-3 BPE, 50257 tokens
for s in ["the cat sat", "dinosaur", "antidisestablishmentarianism"]:
    ids = enc.encode(s)
    print(s, "->", ids, [enc.decode([i]) for i in ids])
output
'the cat sat'                  -> [1169, 3797, 3332]            ['the', ' cat', ' sat']
'dinosaur'                     -> [67, 21317]                  ['d', 'inosaur']
'antidisestablishmentarianism' -> [415, 29207, 44390, 3699, 1042]  ['ant', 'idis', 'establishment', 'arian', 'ism']

the, cat, sat are each one common piece; dinosaur splits into two; the silly long word into five. But every string is representable — that's the open vocabulary that lets one model read the whole internet. This is the "subword middle ground" we mentioned back in 4g, now actually used.

Part 3 · the architecture

Same pipeline as 4g, grown-up recipe

It's still embed → attention → feed-forward → head → softmax with a causal mask — the exact pipeline from Lesson 4. Five small upgrades turn the toy into the GPT-3 architecture:

Piece4g CharGPThere (GPT-3 recipe)
tokensingle characterBPE subword (50,257)
normalisationencoder defaultpre-LayerNorm (LN before attention & MLP)
activationReLUGELU
output headseparate Linearweight-tied to the embedding table
extras—dropout, scaled-residual init
training loopidentical — predict → loss → backward → step → repeat (Lesson 1)

Two of those rows are new words, so meet them before they show up in the code below:

  • pre-LayerNorm. LayerNorm rescales a vector so its numbers don't balloon or vanish — like resetting the volume to a sane level. "Pre" just means we do that rescaling before attention and the feed-forward, not after. Doing it first keeps the signal steady all the way down a deep stack of layers, so training doesn't blow up.
  • GELU. The activation function — the bend that lets a network learn curves, the job ReLU did back in Lesson 1.5. GELU is just a smoother version of that same bend (no sharp corner at zero), and in practice it trains a touch better. Same role, gentler shape.

The config is the GPT-3 family table as code — every dial in one place:

@dataclass
class GPTConfig:
    block_size: int = 128      # context length
    vocab_size: int = 50257    # tiktoken gpt2
    n_layer:   int = 4
    n_head:    int = 4
    n_embd:    int = 192       # d_model — width of every vector
    dropout: float = 0.1

The block wires the two jobs with pre-LayerNorm and residual add — every layer is just x = x + sublayer(ln(x)):

class Block(nn.Module):
    def forward(self, x):
        x = x + self.attn(self.ln_1(x))   # 1. look at neighbours (causal attention)
        x = x + self.mlp(self.ln_2(x))    # 2. think alone (GELU feed-forward)
        return x

And the head shares its weights with the token-embedding table — weight tying, one of the recipe's cheap wins. (The embedding table turns token ids into vectors; the head turns vectors back into scores per token. Tying them means the same grid of numbers does both jobs — fewer parameters to learn, and the two stay consistent.)

self.lm_head = nn.Linear(n_embd, vocab_size, bias=False)
self.tf.wte.weight = self.lm_head.weight   # same numbers do double duty

Underneath, it's the same five-line loop from Lesson 1 — predict, measure the loss, blame each weight, nudge them, repeat. We just add three real-world training tricks on top. None of them changes what the loop does; they just make the downhill walk smoother so a big model trains without blowing up:

  • AdamW — a smarter optimiser than the plain SGD from L1. Instead of one fixed step size for every weight, it gives each weight its own adaptive step based on how it's been moving. (The "W" adds weight decay: a gentle pull keeping the weights from growing too large.)
  • Cosine learning-rate schedule with warmup — the step size isn't constant. It warms up (starts tiny so early steps don't lurch), then eases down along a cosine curve toward the end so the model settles gently instead of overshooting.
  • Gradient clipping — if a gradient ever comes back huge, it gets capped to a maximum size before the nudge. One freak example can't yank the whole model off a cliff.

The actual run from the notebook, on the Mac's GPU:

device = "mps" if torch.backends.mps.is_available() else "cpu"   # Apple GPU
for it in range(601):
    lr = lr_at(it)                       # cosine warmup schedule
    x, y = get_batch(train_data)
    _, loss = model(x, y)                # predict + measure
    loss.backward()                      # blame each weight
    clip_grad_norm_(model.parameters(), 1.0)
    opt.step()                           # nudge them

Part 5 · do it yourself

Run the real one on your Mac

The course/minigpt/ folder has this exact model, sized for an overnight run on TinyStories — a dataset engineered so a ~30M model writes coherent little stories:

This part is watch / optional — you don't have to run it to finish the course. The ideas matter more than typing the commands. If you want to try it, you'll need a terminal (the text window where you type commands), Python 3, and the project's virtual environment (a "venv" — a tidy private box that holds the exact tools this project needs) switched on. If you've never opened a terminal, this is a perfect thing to do with an adult or someone who has. It downloads a few hundred MB and the training can run for a while, so it's fine to leave it going overnight. The text it writes back will be rough and a bit silly — that's completely normal at this tiny scale. 
# from the course/minigpt folder
PY="../../.venv/bin/python"
$PY data.py tinystories --mb 200            # download + BPE-tokenize ~200 MB
$PY train.py --preset tinystories --max_iters 12000
$PY sample.py --ckpt ckpt_tinystories.pt --prompt "Once upon a time"
What is "mps"? It's Metal Performance Shaders — Apple's GPU framework. In PyTorch, device="mps" means "do the math on the Mac's built-in GPU." It's the Apple equivalent of "cuda" on an NVIDIA card. On your M4 it's available, so training runs on the GPU, not the slower CPU.
Reality check — MacBook Air M4 (16 GB, fanless). Memory isn't the bottleneck (16 GB handles a 30M model easily). Heat is — the Air has no fan, so multi-hour runs throttle. Train overnight, keep it cool and plugged in. The true 125M gpt3-small preset is in model.py for reference, but that one really wants a cloud GPU. Want it faster on the Mac? Rewrite in Apple MLX (~2× quicker than PyTorch-MPS here).
