Lesson 5a — House price predictor

The PRAGMA recipe on tabular data, step by step. First we look at the data, then build intuition, then run two experiments and compare.

📓 Open the notebook 🐍 05a_house_predictor.py 📝 Walkthrough
🌉 The bridge: a house is just a short SENTENCE. In L4 the model played fill-in-the-blank on words. A house plays the exact same game — but its "words" are its attributes. 
A sentence of words:       the   cat   sat   on   the   __
A "sentence" of a house:   [bedrooms=3] [bathrooms=2] [area=1800] [garage=yes] [__]
Fill-in-the-blank on a house means: hide one attribute and predict it from the others — exactly like hiding a word and guessing it from the words around it. Hide garage, and the model uses bedrooms, bathrooms, and area to guess it.

Why this is powerful: the model learns how a house's attributes relate to each other with no labels at all — nobody tells it the answer, because the answer is just the attribute we hid. It's the same trick as masked-language-modelling (MLM) on text, pointed at a table instead.

Step 3 How the computer sees each house

The computer doesn't see those nice rows. It sees a flat list of token IDs:

event:  [("bedrooms", "2bed"),
         ("bathrooms", "1bath"),
         ("size",  "small"),
         ...
         ("condition", "faircond")]

ids:    [bedrooms_id, 2bed_id, bathrooms_id, 1bath_id, size_id, small_id, ...]
        ↳ 20 token IDs total (10 keys × 2 each)

The model never sees "rural cottage" as a label. Just a 20-element list of integers. Its whole job is to find structure in those integer sequences.

Step 4 The TWO games the model plays

This is the part that needs to be crystal clear. Pre-training and the downstream task are two separate training sessions on the same data.

🎮 Game 1: Pre-training

Task: fill-in-the-blank on house attributes (mask some values, predict them).

Data: ALL 8,000 houses.

Labels needed? NO — the data labels itself (we hide tokens we already have).

Goal: teach the encoder the correlation structure.

The L4 game from earlier lessons. The model never sees prices here.

🎯 Game 2: Downstream task

Task: predict price class (bargain / cheap / avg / expensive / luxury).

Data: a SMALL labelled set (50, 100, 500, or 4000 houses).

Labels needed? YES — we need the price for each training house.

Goal: classify houses by price.

🔑 The big PRAGMA bet: if Game 1 has taught the encoder something useful about house structure, Game 2 can be done with very few labels — because the encoder already knows the patterns. We just need a tiny "translator" layer (the price head) that maps encoder output → price class.

Step 5 Pre-training, walked through with one concrete house

Take the rural cottage. Encode it. Now randomly mask ~30% of the value tokens (never key tokens — those are the prompt telling the model what KIND of thing to predict):

ORIGINAL:
  bedrooms→2bed  bathrooms→1bath  size→small  age→vintage  neighborhood→rural
  garage→1car    pool→nopool      garden→largegarden       schools→avgschool
  condition→faircond

AFTER MASKING (random 30%):
  bedrooms→2bed  bathrooms→1bath  size→<MASK>  age→vintage  neighborhood→rural
  garage→1car    pool→<MASK>      garden→largegarden       schools→avgschool
  condition→<MASK>

The model looks at the visible context — rural, vintage, 1car, largegarden, avgschool — and uses attention to figure out (once trained):

  • size→<MASK> → rural cottage context → probably small
  • pool→<MASK> → rural + vintage + avgschool → probably nopool
  • condition→<MASK> → vintage + fair-ish profile → probably faircond

The model's guesses (random at first) get compared to the truth. Loss is high → backprop → nudge weights → guesses improve. Run 3,000 times and the encoder learns:

  • "beach" embeddings drift close to "haspool", "largegarden", "exccond"
  • "rural" embeddings drift close to "small", "vintage", "largegarden"
  • "downtown" embeddings drift close to "small", "nogarden", "nopool"

The encoder has learned the archetype structure without being told it exists.

Step 6 How training works (link back to L1)

Same 5-line loop as Lesson 1, just with thousands more weights:

for step in range(3000):
    xb, yb = mlm_mask(X[idx])                   # take a batch, mask some values
    logits = mlm_head(encoder(xb))              # 1. guess
    loss   = loss_fn(logits, yb)                # 2. measure wrongness
    opt.zero_grad()                             # 3. clear notes
    loss.backward()                             # 4. compute gradients for ALL weights
    opt.step()                                  # 5. nudge them

loss.backward() is the magic — it computes gradients for every embedding number, every Q/K/V matrix in attention, every feed-forward weight, and the MLM head — all in one line. We saw exactly how this works in L1c.

After 3,000 steps, the encoder has rich learned representations. We then freeze it and move to Game 2.

Step 7 The downstream task: predict price class

Stack a tiny new layer on top of the frozen encoder:

class PriceHead(nn.Module):
    def __init__(self):
        super().__init__()
        self.proj = nn.Linear(32, 5)   # 32-d encoder output → 5 price classes
    def forward(self, h):
        pooled = h.mean(dim=1)          # average across positions
        return self.proj(pooled)
What is h.mean(dim=1) doing? (mean-pooling) The encoder gives back one vector for every attribute — so a 10-attribute house comes out as 10 separate vectors. But the price head wants a single "summary of the whole house." So we just average all those vectors into one. Think of it like a class vote: each attribute gives its opinion, and we average them into one class opinion that stands for the whole house.

Then train only this head on labelled houses, using the same 5-line loop. The encoder is frozen — opt only knows about the head's parameters.

That's the full embedding probe recipe from PRAGMA §3.1.1.

Step 8 The big experiment: PRE-TRAINING vs BASELINE

This is the comparison the lesson is built around. It's not "pre-trained encoder vs no encoder" — both have an encoder. The difference is what happens BEFORE we train the price head.

PRE-TRAINING recipeBASELINE recipe
Step 1 Train encoder via MLM on all 8,000 houses
(no price labels needed)		 Skip pre-training. Just random-init the encoder.
Step 2 FREEZE encoder
(don't nudge its weights anymore)		 —
Step 3 Add price head Add price head
Step 4 Train price head ONLY on N labelled houses Train EVERYTHING (encoder + head together) on N labelled houses
Why we compare them. We want to know: does the pre-training step actually help? If the baseline (skip pre-training, train end-to-end on labels) does just as well, then pre-training was wasted effort. If the pre-trained recipe wins — especially when labels are scarce — that's the whole foundation-model pitch validated.

Both recipes use the same data, the same architecture, and the same downstream training loop. The only difference is whether we did the self-supervised pre-training step first.

Note: these slider numbers are illustrative — they show the shape of the result (pre-training leads with few labels, baseline overtakes with many). The real accuracy figures come from running the notebook.

What the numbers say

  • 50 labels: pre-training wins by 7 accuracy points. The pre-trained encoder already knows the house structure — the price head just has to learn the small mapping from encoder output → price class.
  • 100 labels: still a small pre-trained edge.
  • 500 labels: baseline overtakes. With more labels, training end-to-end can find encoder representations specifically optimised for price prediction.
  • 4000 labels: baseline wins clearly. End-to-end has enough signal to dominate.
Why isn't pre-training a clear winner everywhere?
  1. Tabular data has limited contextual richness. Only 10 attributes per house. Compare to L5b: 15 events × 4 attributes = 60 correlated pieces of info plus temporal ordering. More structure = more for pre-training to learn.
  2. A frozen encoder is a hard constraint. It can't be tuned for the price task. Once we hit ~500 labels, the baseline's flexibility wins.
Real-world fix: instead of a fully frozen probe, use LoRA fine-tuning (the approach PRAGMA uses) — unfreeze just a small slice of weights during downstream training. You get pre-training's warm start AND the ability to tune for the task. Best of both worlds.

TL;DR What you should walk away with

  1. The PRAGMA recipe (pre-train → freeze → probe) is most valuable when labels are scarce AND the data has rich contextual structure.
  2. Pre-training and downstream are two separate training sessions on the same data. Different goals, different losses, different things being nudged.
  3. The "baseline" comparison is what proves pre-training mattered.
  4. The recipe doesn't ALWAYS win. As you'll see in L5b, with richer sequential data it wins much more decisively — because there's much more structure for MLM to capture.

Green 👑 = pre-training wins (few labels). Yellow 👑 = baseline wins (many labels). The crossover around 500 labels is the lesson: pre-training is a head-start, most valuable when you can't afford many labels.
